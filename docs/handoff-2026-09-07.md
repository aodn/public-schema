## What this session did

1. Implemented a **prototype** Prefect flow at `projects/water_sampling_db/flow.py` (already
   committed as `efc1ea7c WIP: initial download-validate-upload flow (Copilot)`). It downloads each
   `public_schema` Resource's WFS CSV, validates it against its Frictionless schema, and uploads it
   to the `processing-temp-7d-bucket` S3Bucket block. No SQL transforms yet.

2. Ran a `/grill-with-docs` design interview (this repo had **no** `CONTEXT.md`/`docs/adr/`
   anywhere before this session) to design the full ETL, including the SQL transform stage that the
   prototype explicitly skipped. This surfaced and corrected a real mistake mid-session: DuckDB
   cannot run `ALTER TABLE ADD FOREIGN KEY` (confirmed by testing), but **can** enforce the same
   constraint when declared inline in `CREATE TABLE` — so the design pivoted from "drop FK
   validation" to "generate explicit CREATE TABLE DDL with inline PK/FK constraints."

## Current state / what's NOT done

`flow.py` still only implements the Phase 1 prototype (export/validate/upload of raw source
tables). **The transform stage (Phase 3) has not been implemented at all** — only designed. Next
session should implement, in order:

1. Unified dependency graph (source-table FK edges + transform FROM/JOIN edges), topologically
   sorted — see ADR-0001.
2. Per-source-table `CREATE TABLE` DDL generator from each Resource's Frictionless schema
   (`primaryKey` → PK clause, FK `.sql` files spliced in verbatim) — see ADR-0002. **Important:**
   keep column identifiers unquoted in the generated DDL — Frictionless schemas use UPPERCASE
   column names, the transform SQL uses lowercase, and DuckDB's case-insensitive unquoted
   identifier folding is what makes them interoperate. Quoting breaks this silently.
3. Load CSVs into those tables in dependency order; constraint violations block that table's
   downstream transforms (same "skip dependents" policy as a Frictionless validation failure) but
   must not block the raw CSV upload to S3.
4. Execute the ~44 transform SQL files as one Prefect `@task` each, sequentially, in topological
   order (see ADR-0003 for why DuckDB is ephemeral/rebuilt every run — no persistence).
5. CTD Parquet data should be read directly from the `aodn-cloud-optimised` S3 bucket via DuckDB's
   `httpfs` extension — **the exact dataset path/table name in that bucket is still unknown**,
   likely needs coordination with another team.
6. Export Product tables (name ends in `_data`) as CSV, upload to `processing-temp-7d-bucket`
   under a distinct prefix from raw sources; `_map`/other Intermediate tables are never published.
7. Load DuckDB's `spatial` extension — several transforms use `ST_GeomFromText`/`ST_AsWKB`.

## Useful facts discovered during investigation (save yourself the re-testing)

- DuckDB version in `.tox/water_sampling_db` env: 1.5.5 (installed via `pip install duckdb` for
  testing — **not yet added to `requirements.in`/`requirements.txt`**, that still needs doing when
  implementation starts, likely via the `rebuild-requirements` skill)
- `ALTER TABLE ... ADD FOREIGN KEY` → `NotImplementedException` in DuckDB
- Inline `FOREIGN KEY (col) REFERENCES table` (no explicit ref column) in `CREATE TABLE` → works,
  defaults to referencing the target table's primary key
- Composite `PRIMARY KEY (col1, col2, ...)` inline → works; most `public_schema` Resources declare
  composite primary keys (e.g. `bgc_chemistry`: `[TRIP_CODE, SAMPLEDEPTH_M]`)
- All 11 FK `.sql` files in `public_schema` follow one uniform, simple pattern:
  `ALTER TABLE <table>\n    ADD FOREIGN KEY (<col>) REFERENCES <ref_table>\n;` — trivial to parse
- `public_schema`'s SQL transforms are already written in DuckDB dialect (not raw Postgres) per its
  bundled `resources/README.md`, including a documented Postgres→DuckDB translation table
- 8 of the 44 transform `.sql` files use `ST_GeomFromText`/`ST_AsWKB` (spatial extension needed)
- Product vs Intermediate naming rule verified against all 44 transform files with zero
  exceptions: table/view name ends in `_data` → Product; anything else → Intermediate
