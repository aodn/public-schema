# Handoff: water_sampling_db ETL — moving Phase 3 implementation to `aodn/public-schema`

**Origin repo:** aodn/dataflow-orchestration (this doc lives at
`projects/water_sampling_db/docs/handoff-2026-09-15.md`)
**Target repo for next work:** `aodn/public-schema`
**Date:** 2026-09-15

## What changed since the last handoff (2026-09-07)

After external review with other data engineers, we reverted two design decisions from the
2026-09-07 session and reorganized where the implementation will live:

1. **Package split (new — ADR-0004):** Most of the ETL pipeline logic (dependency-ordered
   execution, `CREATE TABLE` DDL generation, source-table load, transform execution, product
   export) will now be implemented in the `aodn/public-schema` package itself, not in
   `dataflow-orchestration`. `dataflow-orchestration`'s `projects/water_sampling_db/flow.py`
   becomes (and stays) a thin Prefect wrapper: it will call `public_schema`'s public API and wrap
   each meaningful step in a `@task` for observability/retries, but own no pipeline logic itself.
2. **Config-driven execution order (reverted from ADR-0001, now ADR-0005):** We are no longer
   building a dependency graph (source-table FK edges + transform `FROM`/`JOIN` edges) with a SQL
   reference parser to infer execution order. Instead, `public_schema` will bundle an explicit
   config file declaring the order/dependency positions of source tables and transforms, replacing
   both the old `aodn/chef-private` data bags and the graph-inference approach.

All four ADRs affected are in `dataflow-orchestration`'s
`projects/water_sampling_db/docs/adr/`:
- `0001-execution-order-via-unified-dependency-graph.md` — now marked **superseded** by 0005
- `0002-pk-fk-constraints-via-create-table-ddl.md` — amended (DDL approach unchanged, but code
  location and order source updated)
- `0003-ephemeral-duckdb-per-run.md` — amended (unchanged decision, code location updated)
- `0004-flow-logic-packaged-in-public-schema.md` — **new**, read this first
- `0005-execution-order-via-config-file.md` — **new**, supersedes 0001, read this second

Also updated in the same repo: `water_sampling_db.md`, `CONTEXT.md` (new terms: **Execution order config**,
**Wrapper flow**), `architecture.md` (diagram redrawn to show the `public_schema`/wrapper-flow
boundary), and `flow.py`'s docstring (a pointer, not new logic — Phase 3 was never implemented
there, so no code needed reverting).

## What is NOT done — this is where `public-schema` work starts

Nothing from Phase 3 has been implemented in either repo yet — the 2026-09-07 session only
designed it, and this session only changed *where* it will be built and *how* order is determined.
Implement, in order, inside `aodn/public-schema`:

1. **Execution order config file.** Design its format (YAML is a natural fit given the rest of the
   package) and location within `public_schema`, alongside the resource descriptors and SQL files.
   It must declare, for every source table and every transform (~44 SQL files), an explicit
   position/stage such that everything it depends on appears earlier. Add a validation/lint check
   (test) that the declared order is internally consistent — it does not need to derive the graph
   from scratch, just verify the declared order doesn't put a dependency after its dependent.
2. **Per-source-table `CREATE TABLE` DDL generator** from each Resource's Frictionless schema
   (`primaryKey` → PK clause, FK `.sql` files spliced in verbatim) — see ADR-0002. **Important:**
   keep column identifiers unquoted in the generated DDL — Frictionless schemas use UPPERCASE
   column names, the transform SQL uses lowercase, and DuckDB's case-insensitive unquoted
   identifier folding is what makes them interoperate. Quoting breaks this silently.
3. **Public API surface** for `dataflow-orchestration` to call: something like
   `load_source_tables(conn, order) -> LoadResult` (loads CSVs into DuckDB tables per the config
   order; constraint violations block that table's downstream transforms — same "skip dependents"
   policy as a Frictionless validation failure — but must not block the raw CSV upload to S3,
   which stays the wrapper flow's job) and `run_transforms(conn, order) -> TransformResult`
   (executes the ~44 transform SQL files in config order; see ADR-0003 for why DuckDB is
   ephemeral/rebuilt every run — no persistence). Keep these functions Prefect-agnostic (plain
   Python, no `@task`) so `public_schema` has no Prefect dependency — the wrapper flow in
   `dataflow-orchestration` wraps them in tasks itself.
4. **CTD Parquet integration.** CTD data should be read directly from the `aodn-cloud-optimised` S3
   bucket via DuckDB's `httpfs` extension — **the exact dataset path/table name in that bucket is
   still unknown**, likely needs coordination with another team. AWS credential wiring for this
   `httpfs` read is also undecided (probably reuse the `AwsCredentials` Prefect block pattern from
   `dataflow-orchestration`'s `common/lib/aws_credentials.py`, but since this code now lives in
   `public_schema`, credential injection needs to be passed in from the wrapper flow rather than
   loaded directly — plan the API accordingly).
5. **Product export.** Tables/views whose name ends in `_data` are Products — export as CSV; return
   them (paths or in-memory) for the wrapper flow to upload to S3 under a distinct prefix from raw
   sources. `_map`/other Intermediate tables are never exported.
6. **Spatial extension.** Load DuckDB's `spatial` extension — 8 of the 44 transform SQL files use
   `ST_GeomFromText`/`ST_AsWKB`.
7. Once the above API exists, come back to `dataflow-orchestration` and rewrite
   `projects/water_sampling_db/flow.py` as the thin wrapper described in ADR-0004 — do not extend
   the current Phase 1 prototype in place, replace it.

## Useful facts carried over from the 2026-09-07 session (still true, save yourself re-testing)

- DuckDB version tested: 1.5.5. `ALTER TABLE ... ADD FOREIGN KEY` → `NotImplementedException`;
  inline `FOREIGN KEY (col) REFERENCES table` in `CREATE TABLE` works and defaults to referencing
  the target table's primary key.
- Composite `PRIMARY KEY (col1, col2, ...)` inline works; most `public_schema` Resources declare
  composite primary keys (e.g. `bgc_chemistry`: `[TRIP_CODE, SAMPLEDEPTH_M]`).
- All 11 FK `.sql` files in `public_schema` follow one uniform, simple pattern:
  `ALTER TABLE <table>\n    ADD FOREIGN KEY (<col>) REFERENCES <ref_table>\n;` — trivial to parse
  for DDL splicing (note: this parsing is still needed for DDL generation, unlike the FK-edge
  graph-inference parser from ADR-0001, which is no longer needed).
- `public_schema`'s SQL transforms are already written in DuckDB dialect (not raw Postgres) per its
  bundled `resources/README.md`, including a documented Postgres→DuckDB translation table.
- Product vs Intermediate naming rule verified against all 44 transform files with zero
  exceptions: table/view name ends in `_data` → Product; anything else → Intermediate.
